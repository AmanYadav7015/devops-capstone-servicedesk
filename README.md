# ServiceDesk

A help desk ticketing system, built as the Session 21 DevOps capstone and shipped through the full
pipeline the course asks for: tests, containers, a GitHub Actions workflow, image scanning, a
container registry, infrastructure as code, a Helm release on Kubernetes, and Prometheus and Grafana
on top.

Support teams live and die by two questions: *what is open right now*, and *what is about to breach
its SLA*. ServiceDesk answers both. A ticket is raised against a queue (a category), given a
severity and a requester, assigned to somebody, and from the moment it is created it carries an SLA
due date twenty-four hours out. The stats endpoint rolls the whole board up into a single response
that the console header and the Grafana dashboard both read.

- Repository: <https://github.com/AmanYadav7015/devops-capstone-servicedesk>
- Images: `ghcr.io/amanyadav7015/servicedesk-backend`, `ghcr.io/amanyadav7015/servicedesk-frontend`
- Live demo walkthrough: [docs/DEMO.md](docs/DEMO.md)
- Step-by-step operator guide: [STUDENT-GUIDE.md](STUDENT-GUIDE.md)

## Scope and originality

ServiceDesk is an original application. The domain, the data model, the API surface, the business
rules and the user interface were all written for this project. Help desk is one of the domains
listed for the final project in the course README, alongside CRM, inventory, booking and the rest.

The DevOps layer deliberately follows the architecture taught in the course — the same shape of
multi-stage Dockerfile, the same job topology in GitHub Actions, the same chart conventions, the
same Prometheus and Grafana stack. The grading policy permits exactly that: *"The application domain
must be your own. The DevOps layer may follow the same architecture."* Nothing in this repository is
a copy of the reference application.

## Domain model

Two tables with a real foreign key between them, so the Alembic migration has something to say and
the API has referential integrity to enforce.

```
┌──────────────────────────────┐          ┌────────────────────────────────────────────┐
│ categories                   │          │ tickets                                    │
├──────────────────────────────┤          ├────────────────────────────────────────────┤
│ id          integer  PK      │◄────┐    │ id           integer      PK               │
│ name        varchar(80) UQ   │     │    │ subject      varchar(200) NOT NULL         │
│ description text             │     │    │ description  text                          │
└──────────────────────────────┘     │    │ severity     varchar(20)                   │
                                     │    │ status       varchar(30)                   │
   Hardware / Network /              └────┤ category_id  integer      FK → categories  │
   Access / Software                      │ requester    varchar(120)                  │
   (seeded by migration 0002)             │ assignee     varchar(120)                  │
                                          │ created_at   timestamptz                   │
                                          │ sla_due_at   timestamptz  default now+24h  │
                                          └────────────────────────────────────────────┘
```

| Field | Rule |
|---|---|
| `severity` | one of `LOW`, `MEDIUM`, `HIGH`, `URGENT`; defaults to `MEDIUM` |
| `status` | one of `OPEN`, `PENDING`, `RESOLVED`, `CLOSED`; defaults to `OPEN` |
| `category_id` | nullable; a value that does not exist is rejected with `422` |
| `categories.name` | unique; a duplicate is rejected with `409` |
| `sla_due_at` | set to creation time plus 24 hours |

A ticket is **breaching SLA** when `sla_due_at` is in the past and the status is still `OPEN` or
`PENDING`. Resolved and closed tickets never count as breaching — that is the whole point of
resolving them.

### API

| Method | Path | Behaviour |
|---|---|---|
| `GET` | `/` | service banner with name and version |
| `GET` | `/health` | liveness, `{"status": "UP"}`, no database touched |
| `GET` | `/ready` | readiness, runs a query so an unreachable database fails the probe |
| `GET` | `/metrics` | Prometheus text exposition |
| `GET` | `/api/categories` | all queues, ordered by name |
| `POST` | `/api/categories` | `201` on create, `409` if the name already exists |
| `GET` | `/api/tickets` | all tickets, newest first |
| `GET` | `/api/tickets/stats` | `{total, open, pending, resolved, closed, breachingSla}` |
| `GET` | `/api/tickets/{id}` | one ticket, `404` if absent |
| `POST` | `/api/tickets` | `201` on create, `422` if `category_id` is unknown |
| `PUT` | `/api/tickets/{id}` | partial update, `404` if absent, `422` if `category_id` is unknown |
| `DELETE` | `/api/tickets/{id}` | `204`, `404` if absent |

Interactive documentation is generated by FastAPI at `/docs`.

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| API | FastAPI with Pydantic v2 | typed request and response models, free OpenAPI docs |
| ORM | SQLAlchemy 2.0 typed mappings | `Mapped[...]` declarations keep the model and the schema honest |
| Migrations | Alembic | two revisions: schema, then the seeded queues |
| Database | PostgreSQL 16 | real relational database, foreign key enforced |
| Console | Vite build served by nginx | small static bundle, nothing to run at request time |
| Metrics | prometheus-fastapi-instrumentator | per-handler counters and latency histograms at `/metrics` |
| Tests | pytest | API tests against an isolated database, never the running one |
| Containers | multi-stage Docker, non-root | build tooling never reaches the runtime layer |
| CI/CD | GitHub Actions | four dependent jobs plus a summary |
| Scanning | Trivy | HIGH and CRITICAL gate on both images |
| Registry | GHCR | images tagged with the full commit SHA |
| IaC | Terraform with the AWS provider | VPC and EKS described in HCL, two modules |
| Orchestration | Kubernetes, packaged with Helm | Deployments, Services, Ingress, HPA, ServiceMonitor |
| Observability | kube-prometheus-stack | Prometheus, Grafana, recording rules, alerts |

## Run it locally

Requires Docker Desktop. Nothing else — Python, Node and PostgreSQL all live inside the images.

```bash
git clone https://github.com/AmanYadav7015/devops-capstone-servicedesk.git
cd devops-capstone-servicedesk
docker compose up --build
```

| Service | URL |
|---|---|
| Console | <http://localhost:3000> |
| API | <http://localhost:8000> |
| API docs | <http://localhost:8000/docs> |
| PostgreSQL | `localhost:5432`, database `servicedesk` |

Ports are overridable: `FRONTEND_PORT=3100 BACKEND_PORT=8100 docker compose up --build`.

The backend container runs `alembic upgrade head` before starting uvicorn, so the schema and the
four seeded queues are in place by the time the API answers. Tear down with
`docker compose down --volumes`.

A quick end-to-end check:

```bash
curl -s localhost:8000/health
curl -s localhost:8000/api/categories
curl -s -X POST localhost:8000/api/tickets \
  -H 'Content-Type: application/json' \
  -d '{"subject":"VPN drops every ten minutes","severity":"HIGH","requester":"a.yadav","category_id":2}'
```

## Run the tests

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
pytest -v
```

The suite points `DATABASE_URL` at a throwaway database created per test session, so it never
touches the PostgreSQL instance from compose or the one in the cluster. The same command runs as the
first job of the pipeline, and a failure there stops the run before any image is built.

## The CI/CD pipeline

`.github/workflows/ci-cd.yml` runs on every push to `main`, on pull requests targeting `main`, and
on manual dispatch.

| Job | Depends on | What it does |
|---|---|---|
| `backend-tests` | — | installs `requirements-dev.txt`, runs `pytest -v` with coverage, uploads `coverage.xml` |
| `frontend-build` | — | `npm install` then `npm run build`, lists and uploads `dist/` |
| `compose-stack` | both above | `docker compose up --build --wait`, proves both containers run as non-root with `id`, exercises the API through the frontend proxy, then reads the rows straight out of PostgreSQL with `psql` |
| `build-scan-publish` | both tests and build | builds both images, runs Trivy, logs in to GHCR and pushes SHA tags |
| `pipeline-summary` | all of the above | writes a result table and the published image references into the run summary |

Image tagging is driven entirely by the commit:

```
ghcr.io/amanyadav7015/servicedesk-backend:<full 40-char sha>
ghcr.io/amanyadav7015/servicedesk-backend:<short 7-char sha>
ghcr.io/amanyadav7015/servicedesk-frontend:<full 40-char sha>
ghcr.io/amanyadav7015/servicedesk-frontend:<short 7-char sha>
```

No `latest` tag is ever published. The deployed revision is therefore always traceable back to one
commit, which is what makes the demo in [docs/DEMO.md](docs/DEMO.md) verifiable rather than
anecdotal. The push steps are skipped on pull requests, so a fork cannot publish into the registry.

## Security scanning

Trivy runs inside `build-scan-publish`, against the images that were just built, before anything is
pushed:

1. **Inventory pass.** `--exit-code 0 --ignorefile /dev/null` prints every HIGH and CRITICAL finding
   on both images, including suppressed ones. This is the honest list, and it is visible in the job
   log whether or not the gate passes.
2. **Gate pass.** `--exit-code 1 --ignore-unfixed --ignorefile .trivyignore.yaml` fails the job on
   any HIGH or CRITICAL vulnerability that has a fix available and is not explicitly excepted.
3. **SARIF export.** Both reports are written as SARIF and uploaded as the `trivy-reports` artifact,
   so findings can be read after the run.

`--ignore-unfixed` is deliberate: a CVE with no upstream patch cannot be fixed by rebuilding, and
failing the build on it only teaches people to disable the gate. Everything that *is* fixable must
be fixed rather than suppressed — which is why `.trivyignore.yaml` currently holds an empty
`vulnerabilities: []` list. Nothing is excepted. The gate passes because the images are clean of
fixable HIGH and CRITICAL findings, not because findings were silenced. The file exists so that a
future exception has an obvious, reviewable home.

Both Dockerfiles are built to keep that list short. The backend installs into a virtualenv in a
builder stage, copies only the virtualenv into a fresh `python:3.12-slim` runtime, runs
`apt-get upgrade`, and then deletes `pip`, `setuptools`, `wheel` and `pkg_resources` from both
site-package trees — those three packages are responsible for a large share of the HIGH findings on
a stock Python image and nothing at runtime needs them. The frontend builds with Node and ships only
`dist/` on `nginx:1.31-alpine`, with `apk upgrade` applied and `cap_net_bind_service` granted to the
binary so nginx can bind port 80 as the unprivileged `nginx` user.

Neither image runs as root: the backend runs as uid `10001`, the frontend as uid `101`. The pipeline
proves it rather than claiming it, with `docker run --entrypoint id` on both images and
`docker compose exec id` on both running containers.

## Terraform — read this plainly

`terraform/` describes a VPC with an internet gateway, two public subnets with public IP mapping
across two availability zones, two private subnets for the workers, a shared NAT gateway, route
tables, and an EKS cluster with IAM roles and a managed node group. `terraform show -json` over the
saved plan counts 35 resources, including `1 aws_vpc`, `4 aws_subnet`, `1 aws_eks_cluster` and
`1 aws_eks_node_group`.

**No AWS account was available for this project, so nothing was ever created in AWS.** That is
stated here rather than buried, because the alternative would be a dishonest submission. What was
actually run:

| Command | Target | Result |
|---|---|---|
| `terraform init`, `fmt -check`, `validate` | AWS provider, offline | clean — [`terraform/evidence/01-init-validate-fmt.txt`](terraform/evidence/01-init-validate-fmt.txt) |
| `terraform plan` | AWS provider, credential checks skipped | 35 resources to add, no errors — [`02-plan-offline.txt`](terraform/evidence/02-plan-offline.txt), [`02b-plan-resource-breakdown.txt`](terraform/evidence/02b-plan-resource-breakdown.txt) |
| `aws sts get-caller-identity` | real AWS | fails, proving no account — [`03-no-aws-account-proof.txt`](terraform/evidence/03-no-aws-account-proof.txt) |
| `terraform apply` | LocalStack on `:4566` | the network module really applies — [`04-localstack-apply.txt`](terraform/evidence/04-localstack-apply.txt), [`05-localstack-state-and-outputs.txt`](terraform/evidence/05-localstack-state-and-outputs.txt) |
| `aws --endpoint-url=http://localhost:4566 ec2 describe-*` | LocalStack | resources exist and match the plan — [`06-localstack-aws-cli-verification.txt`](terraform/evidence/06-localstack-aws-cli-verification.txt) |
| EKS against LocalStack | LocalStack community | not supported, captured rather than faked — [`07-eks-not-supported-by-localstack.txt`](terraform/evidence/07-eks-not-supported-by-localstack.txt) |
| `terraform destroy` | LocalStack | everything torn down — [`08-localstack-destroy.txt`](terraform/evidence/08-localstack-destroy.txt), [`09-post-destroy-verification.txt`](terraform/evidence/09-post-destroy-verification.txt) |

So: the HCL is valid and plans cleanly against the real AWS provider; the networking half has been
genuinely applied and destroyed; the EKS half has been planned but never created, because LocalStack
community does not implement EKS and there is no AWS account to create it in. The Kubernetes
evidence in this project comes from a real minikube cluster instead, which is where the Helm release
actually runs.

Only `terraform.tfvars.example` is tracked. `*.tfvars`, `*.tfstate*`, `.terraform/` and plan files
are all ignored, and no AWS key has ever been committed. Full detail, including what it would cost
and what to change for a real account, is in [`terraform/README.md`](terraform/README.md).

## Kubernetes and Helm

The chart is `helm/servicedesk`, installed into the `servicedesk` namespace.

```bash
kubectl apply -f k8s/namespace.yaml
helm upgrade --install servicedesk helm/servicedesk \
  --namespace servicedesk \
  --set backend.image=ghcr.io/amanyadav7015/servicedesk-backend \
  --set frontend.image=ghcr.io/amanyadav7015/servicedesk-frontend \
  --set backend.tag=<commit-sha> \
  --set frontend.tag=<commit-sha> \
  --wait
```

The chart's committed defaults point at locally built images so that it installs on a cluster with
no registry access; the command above is the registry path, and it is the one the demo uses.

| Object | Detail |
|---|---|
| `Deployment` backend | 2 replicas, `runAsNonRoot`, all capabilities dropped, init container waits on PostgreSQL |
| `Deployment` frontend | 2 replicas, `runAsNonRoot` |
| `Deployment` postgres | single replica with a 2Gi PVC, credentials from a `Secret` |
| `Service` x3 | all `ClusterIP`; the backend also gets a short `backend` alias used by in-cluster checks |
| `Ingress` | `servicedesk.local`, `/api` to the backend, `/` to the frontend |
| `HorizontalPodAutoscaler` | backend, 2 to 6 replicas, target 60% CPU |
| `ServiceMonitor` | rendered only when the Prometheus operator CRDs are installed |

Probes are split by purpose: a `startupProbe` on `/health` gives a cold container up to 150 seconds
to finish migrating, a `readinessProbe` on `/ready` pulls a pod out of the Service if the database
goes away, and a `livenessProbe` on `/health` restarts a genuinely wedged process. The backend
Deployment carries a `checksum/secret` annotation so that changing the database credentials rolls
the pods instead of leaving them on stale environment variables.

`values-dev.yaml` drops everything to one replica with no persistence and no autoscaling;
`values-prod.yaml` raises replicas to three, grows the volume and widens the HPA to 3–10.

**macOS caveat.** On the Docker driver the node IP `192.168.49.2` is not routable from the host, so
`curl http://servicedesk.local` from a Mac terminal will hang no matter what is in `/etc/hosts`.
Reach the application with `minikube ssh -- curl -H 'Host: servicedesk.local' http://192.168.49.2/`
or with `kubectl port-forward`. [STUDENT-GUIDE.md](STUDENT-GUIDE.md) gives both recipes.

## Observability

The backend exposes Prometheus metrics at `/metrics` through
`prometheus-fastapi-instrumentator`: `http_requests_total` by handler, method and status, and
`http_request_duration_seconds` as a histogram, alongside the standard process and Python collectors.

`monitoring/install.sh` installs `kube-prometheus-stack` into the `monitoring` namespace with
Prometheus on NodePort 30250 and Grafana on 30251, and loads
`monitoring/grafana-dashboard-servicedesk.json` as a sidecar-provisioned dashboard. The admin
password is read from `GRAFANA_ADMIN_PASSWORD` and the script refuses to run without it — there is
no password in the repository.

Scraping is belt and braces: the chart's `ServiceMonitor` is the primary path, and
`prometheus-values.yaml` also carries an endpoint-discovery scrape job keyed on the
`app=servicedesk-backend` service label, so metrics keep flowing even if the operator's selectors
are misconfigured. On top of the raw series there are recording rules for request rate, error ratio,
p95 latency and the proportion of ticket API calls served inside a 300ms budget, plus three alerts:
backend not scraped, error ratio above 25%, and more than 10% of ticket calls over budget.

Full narrative, PromQL and captured output: [`monitoring/README.md`](monitoring/README.md).

## What is complete, and what is partial

Honest accounting, module by module.

**Complete.**

- **M1 Application.** Backend, frontend, PostgreSQL, two tables with a foreign key, Alembic
  migrations including a seed revision, twelve endpoints covering all four verbs.
- **M2 Testing.** pytest suite against an isolated database, gating the pipeline.
- **M3 Git and GitHub.** Public repository, well over ten descriptive commits, `.gitignore` proven
  to cover every required path, and a gitleaks scan over the full history.
- **M4 Docker.** Both Dockerfiles multi-stage, both non-root, compose brings up all three services
  and is smoke tested in CI on every push.
- **M5 CI/CD.** Five jobs, triggered on push to `main`, tests gate the build, both images published
  to GHCR under the commit SHA with no `latest` tag.
- **M6 DevSecOps.** Trivy on both images with a real failing gate, an unsuppressed inventory pass
  next to it, and SARIF artifacts.
- **M8 Kubernetes and Helm.** Chart deployed to a live minikube cluster in the `servicedesk`
  namespace, two replicas per tier, ClusterIP services, working Ingress, HPA and ServiceMonitor.
- **M10 Documentation and demo.** This README, [STUDENT-GUIDE.md](STUDENT-GUIDE.md), and a captured
  end-to-end demo in [docs/DEMO.md](docs/DEMO.md).

**Partial, and why.**

- **M7 Terraform.** The HCL is complete and plans cleanly, and the VPC half has been genuinely
  applied, verified and destroyed — but against LocalStack, not AWS. The EKS cluster has never been
  created, because there is no AWS account and LocalStack community does not implement EKS. The
  rubric's "AWS Console screenshot showing VPC and EKS cluster" cannot be produced and is not
  claimed.
- **M9 Observability.** Prometheus and Grafana are installed in the cluster, the backend is scraped,
  the dashboard is provisioned and its panels return data — all verified through the Prometheus and
  Grafana HTTP APIs. What does not exist is a browser screenshot of the rendered dashboard.
